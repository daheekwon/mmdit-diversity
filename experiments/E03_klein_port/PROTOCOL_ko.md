## 1. 목적

우리 방법(image V 편집 + pad V 감쇠)을 세 번째 MMDiT 모델인 FLUX.2-klein-base-4B에 같은 방식으로 옮긴다.
그리고 dev, ho3, COCO48에서 다양성 증가와 비용을 SD3.5·FLUX.1과 같은 지표로 잰다.

## 2. 모델 설정

- 모델: `black-forest-labs/FLUX.2-klein-base-4B` (revision a3b4f48). 증류하지 않은 base 모델이다.
- 생성: 512×512, 50 step, CFG 4.0. 텍스트는 Qwen3 chat template을 512칸까지 채운다.
- CFG는 step마다 transformer를 두 번 부른다(조건 prompt, 빈 prompt 순서).
- 텍스트 마스크가 없다. 그래서 pad 칸도 attention을 받는다. 예: "A red panda"는 512칸 중 497칸이 pad다.
- 블록 번호는 전역 번호다. double 블록은 0–4, single 블록은 5–24다.
- 구현: `configs/klein.yaml`, `div/models.py`의 `_KleinProcessor`.

## 3. 방법 이식

같은 방법 규칙을 따른다. 건드리는 모듈과 조작 종류는 SD3.5·FLUX.1과 같고, 강도와 블록·step 범위만 다르다.

### 3.1 V편집

- image V 행에 `V' = V + (λ−1)·Q·Qᵀ·V`를 적용한다. klein에는 V bias가 없다.
- `Q`는 블록별 seed 대비 기저다. `D/trD − C/trC`의 상위 256개 고유벡터다.
- 조건 호출과 빈 prompt 호출을 모두 편집한다. SD3.5에서 CFG 두 행을 모두 편집한 것과 같다.

### 3.2 기저 적합

- 원본 모델로 적합한다.
- prompt와 seed는 FLUX.1·SD3.5 기존 기저와 같다: dev 일반 prompt 8개 × seed 40000–40015(16개).
- CFG 두 호출을 모두 모으고, 전 블록(0–24)을 모은다.
- step 구간마다 기저를 따로 만든다: step 0–4용 기저, step 0–6용 기저. 이전 모델들처럼 모으는 step이 편집 step과 같다.
- 두 기저는 한 번의 실행에서 같이 모은다(`basis.StepSets`). CPU 시험에서 따로 모은 결과와 비트 단위로 같았다.
- 명령: `fit_basis.py --model klein --name klein_dev8 --dataset dev8 --steps 0-4 0-6`

### 3.3 pad V

- image query 행이 pad 칸의 value를 ×¼로 읽는다. ¼은 FLUX.1과 같은 값이다(사용자 결정 2026-11-05).
- 전 블록(0–24)에 적용한다. step은 V편집과 같다(pad와 V 같은 step 규칙).
- pad 위치는 조건 prompt의 Qwen 패딩 칸이다. 빈 prompt 호출에서도 같은 위치를 쓴다. 그 칸은 빈 prompt 쪽에서도 패딩이다(SD3.5와 같은 규칙).

### 3.4 구현 확인 (GPU, `tests/parity_klein.py`, 11-05)

다음 경우 모두 diffusers 원래 파이프라인과 픽셀이 완전히 같았다(prompt "A red panda", seed 2개).

- 원본
- V편집 λ1 (전 블록, 전 step)
- pad ×1 (전 블록, 전 step)
- DAVE α1 (double 블록 2, single 블록 13)

λ1.5 + pad ¼ 시험 실행에서는 attention 호출이 250번 편집되었다(25 블록 × 5 step × 2 호출). CPU 시험 31개도 통과했다.

### 4.1 블록 범위의 근거

- 5–24: single 블록 전체.
- 10–15: 사용자가 지정했다(11-05). 전역 번호다(single 블록 6~11번째).
  - FLUX.1의 19–37은 깊이 33–65%다. 이를 klein 25블록에 깊이 비율로 옮기면 8–16이다. 10–15는 그 안에 든다.
  - 결과를 보고 고른 범위가 아니다. 그래도 사전 기준으로 정한 범위도 아니다. 블록 규칙상 기본값은 "single 전체"다. 그래서 10–15를 채택하려면 single 전체보다 낫다는 근거가 필요하다.
- 0–24: 전 블록(double 0–4 + single 5–24). 사용자가 추가했다(11-05 12:30, dev 생성 중, 지표 계산 전).
  - SD3.5에서 채택한 "전 블록" 기준과 같다. 기저는 이미 전 블록(0–24)에서 모았으므로 그대로 쓴다.
  - 5–24와 0–24는 둘 다 사전 기준 범위("전부")다. 둘의 비교는 같은 Vendi에서 비용으로 보고하고, 채택은 사용자가 정한다.
  - dev 0–24 10개는 `run_extra_dev.sh`로 따로 생성한다. ho3와 COCO48에서는 드라이버 작업 목록에 들어 있다.

## 6. 판정 규칙 (결과 전 고정)

1. ΔVendi = 조건 − Original. prompt 평균을 쓰고, prompt bootstrap으로 95% 구간을 낸다.
2. DAVE 대비 판정은 generalize와 같은 규칙이다.
   - 규칙 1 (다양성): 우리 ΔVendi ≥ DAVE ΔVendi.
   - 규칙 2 (비용): DAVE 대비 깨짐 차 ≤ +2%p, 불일치 차 ≤ +2%p, MUSIQ 차 ≥ −1 (점추정).
3. 통과: ho3와 COCO48 모두에서 규칙 1·2를 통과한 조건. dev는 표본 내라서 참고로만 본다.
   - 11-05 20:00 변경: 규칙 1·2의 DAVE는 step 0–10 DAVE다(§4.4). step 0–19 DAVE는 ho3에서 돌리지 않는다.
   - 11-05 변경: COCO48을 돌리지 않으므로 지금은 ho3만으로 판정한다. 이 판정은 잠정이다. COCO48을 나중에 돌리면 원래 규칙으로 다시 판정한다.
4. 이식이 작동한다는 최소 조건(DAVE 없이도 판단): ho3와 COCO48에서 ΔVendi 95% 구간이 0보다 크고, λ가 커지면 함께 커진다.
5. 품질에 관한 주장은 이미지 시트를 확인한 뒤에만 한다. 판정기가 놓치는 실패가 있었다(흑백 그래픽, 노이즈 패턴).
6. 블록 10–15를 single 전체 대신 채택하려면 같은 Vendi에서 비용이 더 낮아야 한다. 같은 Vendi는 λ 곡선 보간으로 맞춘다.
7. 블록 0–24와 5–24는 같은 Vendi에서 비용을 비교해 보고한다(둘 다 사전 기준 범위).

  - 그래서 klein의 두 구간은 이전 모델보다 훨씬 이른 잡음 구간만 편집한다.
- 효과가 약하게 나오는 경우, 사후 제안 후보: σ로 맞춘 구간을 추가한다. 예: 0–9는 SD3.5 0–3과, 0–19는 FLUX.1 0–5와 σ가 같다. 이 경우 별도 프로토콜을 쓴다.
- klein Original은 이미 다양성이 낮아 보인다(파리티 이미지에서 두 seed 모두 정면 클로즈업). 확인은 dev Original 시트에서 한다.

## 11. COCO48 확인 실험 (2026-11-06, 결과 전에 고정)
- 이유: 우리 λ1.5(블록 0–24, V·pad V ¼ 스텝 0–10)를 ho3 결과를 보고 klein 최종 후보로 골랐다. ho3는 더 이상 보지 않은 데이터가
  아니므로, 손대지 않은 COCO48에서 확인한다 (사용자 11-06 "네, 큐에 넣어").
- 조건 3개: Original, DAVE α0.2 블록 13 스텝 0–10 (`dave_a0.2~0-10`), 우리 λ1.5 (`q_l1.5@0-24~0-10+pad_v0.25~0-10`,
  basis `bases/klein_dev8_s0-10_k256.pt`). COCO48 = 48 prompt × seed 68000–68015. 다른 조건은 돌리지 않는다.
- 측정: ho3와 같다 (Vendi DINO, 판정기, MUSIQ, CLIP-text). 사전 규칙 1·2 (DAVE 0–10 대비)는 그대로 계산해 적는다.
- 확정 기준 (둘 다 맞으면 λ1.5를 klein 최종으로 본다):
  1. 눈으로 센 실패 수: λ1.5 ≤ DAVE 0–10 (768장 중 장수, 점추정).
  2. 실패를 뺀 Vendi (prompt마다 세 조건을 같은 장수 k로 맞춤, 500번 추출 평균): λ1.5 − DAVE의 95% prompt bootstrap 구간이
     0을 포함하거나 0보다 위 (DAVE보다 유의하게 낮지 않음). 점추정도 적는다.
  판정기 불일치가 DAVE보다 +2%p를 넘으면 (dev에서 +10.7%p였다) 기준과 별도로 사용자에게 알린다. 기준에는 넣지 않는다.
- 눈으로 세는 방법: blind_count/CRITERIA_ko.md의 실패 종류 그대로. 바꾸는 점: 썸네일 256 px (ho3에서 192 px는 유화 화풍을
  숨겼다), 한 시트 = prompt 하나 × 세 조건 (순서 무작위, A–C) × seed 8개. 셈을 고정한 뒤 조건을 열고, 판정기만 깨졌다고 본
  이미지를 원본 크기로 다시 본다 (조건을 알고 함, ho3와 같음). k < 6인 prompt는 Vendi에서 빼고 수를 적는다.
- 실행: `run_coco48_confirm.sh`, GPU 0·3 (11-05 19:53 사용자 지시 유지), 조건마다 prompt를 두 shard로 나눠 6 job. 생성 →
  빠진 이미지 재실행 → link → 평가 (eval + judge) → report → `blind_count/make_blind_coco48.py`로 가린 시트.
  driver.log에 "COCO48_DONE". 다른 세션(E06)이 GPU를 쓰는 동안은 lanes 메모리 검사(16 GiB)로 기다린다.
