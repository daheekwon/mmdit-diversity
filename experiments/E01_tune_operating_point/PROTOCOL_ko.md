# E01 새 기저 확인 (tune) → 전체 규모 비교

상태: **초안 2판 (2026-11-05)**. 11-04 초안을 11-05에 정한 설정(모든 block에 같은 λ)에 맞춰 다시 썼습니다. 바뀐 점은 맨 끝 절에 있습니다. §8의 남은 항목(5, 9–11)이 정해진 뒤, 생성을 시작하기 전에 고정합니다. 고정한 뒤에는 결과를 보고 고치지 않습니다. 고칠 일이 생기면 이 파일 끝에 날짜를 붙여 덧붙입니다.

## 1. 목적

1. 새 보정 prompt로 V편집 기저를 적합합니다.
2. 처음 쓰는 tune prompt에서 새 기저가 이전 기저와 비슷하게 동작하는지 확인합니다.
   - 운영점(λ, block, step)은 미리 고정합니다. tune에서 고르지 않습니다.
   - λ 곡선은 논문 그림용과 나중 판단용으로만 그립니다.
3. 고정한 운영점으로 ImageNet 1000 × 10장, COCO 500 × 10장 전체 평가를 합니다. Original, DAVE 기준 세팅, CADS와 나란히 비교합니다.

DAVE 기준 세팅은 DAVE를 돌리는 설정일 뿐입니다. 우리 강도를 DAVE의 Vendi나 비용에 맞추지 않습니다.

## 3. 데이터 (세 묶음은 서로 겹치지 않음)

| 묶음 | 내용 | seed |
|---|---|---|
| 보정 (기저 적합) | 사용자가 정할 prompt 파일 | 9000000 + i (16개) |
| tune | COCO 50 + ImageNet 50 = 100 prompt × 10장 | COCO 3000000 + 100·i + j, ImageNet 2000000 + 100·i + j |
| test (전체 규모) | ImageNet 1000 클래스 × 10장, COCO 500 캡션 × 10장 | ImageNet 0 + 100·i + j, COCO 1000000 + 100·i + j |

- **COCO tune:** test 500장에 들어가지 않은 val2017 이미지 4,500장 중 50장을 `random.Random(0)`으로 뽑습니다. 이미지마다 캡션을 하나씩, 같은 난수로 고릅니다. 파일은 COCO 캡션 형식으로 만듭니다(`coco/captions_val2017_tune50.json`).
- **ImageNet tune:** 클래스는 1000개뿐이라 test와 겹칠 수밖에 없습니다. 그래서 고정 섞기 순서의 처음 50 클래스를 쓰고, seed를 test와 다르게 해서 이미지가 겹치지 않게 합니다.
- 보정 prompt는 이전 개발 prompt(dev, ho2–ho4)와도, tune·test와도 겹치면 안 됩니다.
- **λ를 정한 COCO 48과 겹치는 사진은 바꿨습니다(사용자 11-05, §8-7).**
  - 처음 파일에서는 캡션은 겹치지 않았지만, COCO 48과 같은 사진에 다른 캡션을 단 경우가 test에 5개, tune에 1개 있었습니다.
  - 이 6개를 같은 행에서 다른 val2017 사진으로 바꿨습니다. 새 사진은 test, tune, COCO 48 어디에도 없는 사진 중에서 `random.Random(1)`로 고르고, 캡션도 같은 난수로 하나 고릅니다. 같은 행에서 바꾸므로 나머지 prompt의 seed는 그대로입니다.
  - test 파일: `coco/captions_val2017_img500_cap500_no_coco48.json` (원본 `captions_val2017_img500_cap500.json`은 그대로 둠). 495개는 원본과 같습니다. 바뀐 행은 30, 272, 392, 432, 433입니다.
  - tune 파일: `coco/captions_val2017_tune50_no_coco48.json`. 바뀐 행은 42입니다.
  - 바꾼 목록(이전·새 사진 번호와 캡션)은 `coco_replaced.json`에 있습니다.
  - 그래서 COCO test는 DAVE 논문 규모의 500 캡션 파일과 5개가 다릅니다. 이 점은 논문에 밝힙니다.

## 5. 새 기저 확인 (강도를 고르지 않음)

모든 값은 같은 prompt·seed로 짝지은 Original 대비 차이입니다. prompt 평균과 95% bootstrap 구간을 씁니다.

전체 규모로 넘어가기 전에 아래 두 가지를 봅니다.

1. 새 기저 운영점이 COCO tune과 ImageNet tune 둘 다에서 Vendi(DINO)를 Original보다 올리는지 봅니다(95% 구간이 0보다 큼).
2. 이미지 시트(데이터셋마다 10 prompt × 10장)를 봅니다. Original, 이전 기저 운영점, 새 기저 운영점을 나란히 둡니다. 이전 기저에 없던 실패 형태가 새 기저에서 생기는지 봅니다.
   - 실패 형태: 알아볼 수 없는 실루엣, 알아볼 수 없는 근접, 흑백 평면 그래픽, 무늬·노이즈 붕괴, 개념 상실.
   - 어둡지만 알아볼 수 있는 근접은 실패가 아닙니다.

두 가지를 모두 통과하면 고정한 운영점 그대로 전체 규모로 갑니다. 하나라도 걸리면 전체 규모 전에 멈추고 사용자와 다시 정합니다. 이때 강도를 자동으로 다시 고르지 않습니다.

다음은 함께 보고합니다. 멈춤 조건이 아닙니다.
- 운영점끼리의 차이: Vendi(DINO), CLIP score, ImageReward.
  - 새 기저 − 이전 기저.
  - SD3.5만: 새 기저 step 0–3 적합 − 이전 기저. 보정 prompt만 다릅니다.
  - SD3.5만: 새 기저 step 0–11 적합 − step 0–3 적합. 적합 step만 다릅니다.
- 각 기저에서 λ가 만드는 image V 상대 변화량: (λ−1) × 편집 block의 단위 평균.
- SD3.5 이미지 시트에는 step 0–3 적합 기저의 행도 넣습니다.

## 6. 예측 (판정에는 쓰지 않음, 해석용)

이전 기저로 낸 ho3·COCO 48 결과(512, prompt마다 16 seed)를 바탕으로 적습니다. 이 실험은 1024이고 prompt마다 10장이라 Vendi 값의 크기가 다릅니다. 그래서 방향과 순서만 예측합니다. 1024에서는 이 예측이 맞지 않을 수 있습니다(§2 해상도).

| 모델 | 데이터 | 우리 Vendi 증가 | DAVE Vendi 증가 |
|---|---|---|---|
| SD3.5 λ1.14 + pad ¼ | ho3 | +1.22 | +1.06 |
| SD3.5 λ1.14 + pad ¼ | COCO 48 | +0.96 | +0.92 |
| FLUX λ1.72 (실제 1.7196) | ho3 | +1.43 | +1.30 |
| FLUX λ1.72 (실제 1.7196) | COCO 48 | +1.13 | +0.91 |

1. 새 기저 운영점의 Vendi(DINO) 증가는 이전 기저 운영점과 비슷합니다(차이의 95% 구간이 0을 포함). 이전에 새 prompt에서도 기저 방향 범위는 같았기 때문입니다(seed 편차 포착 비율 1.00).
2. 우리 운영점은 두 모델, 두 데이터셋 모두에서 Vendi(DINO)를 Original보다 올립니다.
3. 두 모델 모두 우리 Vendi 증가가 DAVE 기준 세팅 이상입니다. 차이가 작아서(SD3.5 COCO 48 +0.04, FLUX ho3 +0.13) 데이터셋에 따라 뒤집힐 수 있습니다.
   - 1024에서는 이전 운영점 기준으로 SD3.5의 우리 효과가 커졌고 FLUX의 DAVE 효과가 약해졌습니다. 그래서 1024에서는 우리가 DAVE보다 더 앞설 수 있습니다. 대신 SD3.5 비용도 커질 수 있습니다.
4. 비용은 이전과 같은 형태로 나옵니다.
   - SD3.5: 일부 prompt에서 평면 일러스트, 흑백 그래픽(ho3의 toucan). 1024에서는 흑백 실루엣이 더 많을 수 있습니다.
   - FLUX: 일부 prompt에서 평면 일러스트 seed(COCO 48의 자동차, 점심).
   - 화질(MUSIQ)은 DAVE보다 낮습니다(이전 −1.3에서 −1.8).
5. λ 곡선의 Vendi(DINO)는 λ가 커질수록 올라갑니다.
6. 전체 규모에서도 우리와 DAVE의 Vendi 순서는 tune과 같습니다.

    - `fit_basis.py`는 설정의 해상도(이제 1024)로 적합합니다. 수집은 prompt 하나의 16 seed를 한 번에 생성합니다.
    - FLUX 1024 배치 8의 생성에 GPU 메모리 34 GiB를 잡았었습니다. 16 seed를 한 번에 생성하면 48 GiB GPU에 들어가지 않을 수 있습니다.
    - 다른 안: 이전 기저처럼 512에서 적합합니다. 지금 `fit_basis.py`에는 해상도를 바꾸는 옵션이 없어서 하나 추가해야 합니다.
11. **1024의 배치 크기와 필요 메모리.** §2의 배치 10과 `e01.py`의 필요 메모리(SD3.5 22 GiB, FLUX 32 GiB)는 512 기준입니다. 1024 배치 10은 아직 재지 않았습니다. 생성 전에 한 번 재고 정합니다.

## 9. 실행 순서와 시간

1. 기저 적합: 두 모델, 보정 prompt × 16 seed, 전 block, §8-10의 해상도. SD3.5는 step 0–11과 0–3, FLUX는 step 0–5.
2. tune 생성과 평가 → §5 확인 → 결과를 이 파일 끝에 기록합니다.
3. 전체 규모 생성과 평가 → 보고(`ANALYSIS_ko.md`).

GPU 시간 (평가 시간과 GPU 대기 시간은 빠짐):

| 단계 | SD3.5 | FLUX |
|---|---|---|
| 기저 적합 | 512에서 약 2–3시간 (1024는 몇 배, 재지 않음) | 512에서 약 1시간 (1024는 몇 배, 재지 않음) |
| tune (SD3.5 12,000장, FLUX 11,000장) | 약 38 GPU시간 | 약 94 GPU시간 |

## 10. 구현

- `configs/data.yaml`, `div/data.py`: tune 데이터셋 `imagenet_tune`(50 클래스, seed 2000000), `coco_tune`(캡션 파일, seed 3000000). test와 seed·COCO 이미지가 겹치지 않음을 테스트로 확인합니다.
- `e01.py coco-sets`: COCO test·tune 캡션 파일을 만듭니다(§3, 만들어 둠). tune 50장을 뽑는 단계는 11-04 파일(`captions_val2017_tune50.json`)과 같은 결과를 내는지 확인합니다.
- `e01.py check-calib`: 보정 prompt가 tune·test prompt, 그리고 `value_diversity/results`의 모든 생성 prompt(1,700여 개)와 겹치는지 검사합니다. 겹치면 멈춥니다.
- `e01.py jobs`: §4·§7의 조건을 GPU 작업 목록으로 씁니다. 기저 이름과 적합 step은 `FIT`, 운영점 기저는 `BASIS`, SD3.5 참고 기저는 `REF`입니다.
- `scripts/sheet.py`: 나란히 놓는 시트, 조건을 가리고 섞은 시트와 정답표, 라벨을 모아 조건별 실패 수를 내는 집계.
- `scripts/lanes.py`: GPU마다 한 번에 한 작업씩 돌립니다.
  - 작업마다 필요한 메모리 여유를 30초 간격으로 두 번 확인한 뒤 시작합니다.
  - OOM이면 다시 시도합니다(최대 5번).
  - `state.json`에 상태를 남겨, 다시 시작하면 끝난 작업을 건너뜁니다.
- `run.sh` 단계: `coco-sets` → `basis`(CALIB=<보정 파일>) → `tune` → `report`(§5 표와 시트) → `full`.
  - 필요한 메모리 여유: SD3.5 22 GiB, FLUX 32 GiB.
  - 기본 GPU는 1 2 3입니다(`GPUS`로 바꿈).
