# 최종 방법을 1024로 옮기기 (COCO 48 prompt)

상태: **고정 (2026-11-05)**. 사용자 요청: "새로운 최종 방법을 1024로 돌려보고싶어".
- 같은 날의 이전 초안(성분 나누기, FLUX 스케줄 고정, 노이즈 수준 맞춤 step)은 사용자가 대화에서 줄였다. 이번에는 최종 방법 하나만 512와 1024에서 비교한다.
- 고정한 뒤 고칠 일이 생기면 끝의 변경 기록에 날짜를 붙여 적는다.

## 1. 질문

1. 512에서 정한 최종 방법이 1024에서도 DAVE 표준 세팅 대비 같은 판정을 받는가.
2. 1024에서 최종 방법의 효과와 비용이 512와 비슷한가.

## 2. 최종 방법 (2026-11-05 사용자 결정, `configs/sd35.yaml`, `configs/flux.yaml`의 `ours` 프리셋)

| | SD3.5 | FLUX |
|---|---|---|
| V편집 블록 | 전 블록 0–23 | single 19–37 |
| V편집 λ | 1.14 (모든 블록에 같은 λ) | 1.72 (모든 블록에 같은 λ) |
| pad V | ×¼, 전 블록 | ×¼, 전 블록 |
| V와 pad의 step | 둘 다 0–11 | 둘 다 0–5 |
| 기저 | `bases/sd35_legacy_dev8_b0to23_k256.pt` | `bases/flux_legacy_dev8_k256.pt` |
| CFG | 두 갈래 모두 편집 | (갈래 없음) |

- 설정 파일 그대로 쓰고, 해상도만 명령줄에서 바꾼다.
- FLUX는 해상도에 따라 노이즈 스케줄이 바뀐다(μ 0.63 → 1.15). 표준 파이프라인 그대로 둔다.

## 3. 데이터

- prompt는 COCO 48개(coco_00–47), seed는 68000–68007이다. E01과 같다.
- Original과 DAVE 표준 세팅(SD3.5 α0.5 블록 6 step 0–3, FLUX α0.2 블록 30 step 0–5)은 E01의 512·1024 이미지와 판정기 결과를 그대로 쓴다(링크).
- 최종 방법은 512와 1024 모두 이 패키지로 새로 만든다. 묶음은 8장이다(E01 우리 방법과 같음).
  - SD3.5: 이전 실행기는 bf16 경로가 달라 픽셀이 다르다(E01 변경 기록).
  - FLUX: 이전 실행은 λ1.7196이었다. 설정의 λ1.72와 달라 픽셀이 같지 않다.
- 그래서 이번 512 수치는 이전 512 결과(seed 16개, 이전 실행기)와 조금 다를 수 있다. 판정에는 이번 512를 쓴다.

## 4. 관문 (생성 시작 직후)

- 첫 prompt의 `meta.json`에서 λ(SD3.5 1.14, FLUX 1.72), 편집한 어텐션 호출 수, pad 토큰 수를 확인한다. 설정과 다르면 멈춘다.

## 5. 평가 (E01과 같다)

- 1024 이미지는 Lanczos로 512로 줄여 판정기, MUSIQ, CLIP, DINO에 넣는다. 시트는 1024 원본을 쓴다.
- 다양성은 Vendi(DINO)이다.
- 깨짐은 p_defect ≥ .5 또는 p_style ≥ .5, 불일치는 p_match < .5이다. 판정기 이름은 `combo_R`(Qwen3-VL-8B)이다.
  - 판정기는 최종 방법 이미지에만 새로 돌린다. Original과 DAVE는 E01의 같은 판정기 결과를 쓴다.
- 구간은 prompt 단위 paired bootstrap 10,000회로 낸다. 모든 비교에 같은 표본을 쓴다.
- ΔVendi와 비용은 같은 해상도의 Original 대비로 잰다.

## 6. 판정 규칙 (결과를 보기 전에 고정)

**판정 1 — DAVE 대비 (512 최종 선택 때의 규칙 그대로, 해상도마다):**
- 다양성: 최종 방법 ΔVendi ≥ DAVE ΔVendi (점추정).
- 비용: 깨짐 − DAVE ≤ +2%p, 불일치 − DAVE ≤ +2%p, MUSIQ − DAVE ≥ −1 (점추정, 구간 병기).
- 모두 만족하면 그 해상도에서 "통과"다.

**판정 2 — 512와 비슷한가 (모델마다):**
- 1024 ΔVendi ÷ 512 ΔVendi가 0.67 이상 1.5 이하이다 (점추정, 구간 병기).
- Original 대비 깨짐과 불일치의 증가가 1024에서 512보다 +2%p 넘게 크지 않다.
- Original 대비 MUSIQ 변화가 1024에서 512보다 1 넘게 나쁘지 않다.
- 모두 만족하면 "512 설정이 1024로 그대로 옮겨진다"다.

**판정 3 — 이미지 (정성):**
- prompt 하나당 그림 하나로 만든다. 행은 조건(Original, DAVE, 최종 방법)이고, 512와 1024를 나란히 둔다.
- prompt는 E01과 같은 12개(coco_00, 04, …, 44)와 판정기의 최종 방법 깨짐 상위 4개이다.
- 실패 유형: SD3.5는 흑백 평면 그래픽과 실루엣, FLUX는 3D 만화, 아이소메트릭, 평면 일러스트, 확대와 잘림이다.
- 알아볼 수 있는 어두운 근접 사진은 실패로 세지 않는다(사용자 규칙 2026-11-03).

**해석:**
- 1024에서 판정 1과 판정 2를 모두 통과하면, 최종 방법을 1024에서 그대로 쓴다.
- 판정 2에서 효과가 1.5배를 넘으면, 같은 λ가 1024에서 더 세게 작동한다는 뜻이다. 1024의 λ는 사용자가 따로 정한다. 이번 COCO 48로 λ를 고르지 않는다.
- 1024에서 판정 1이 실패하면, 실패한 항목과 이미지 유형을 보고한다.

## 7. 비용과 순서

| 묶음 | 이미지 | 예상 GPU-시간 |
|---|---|---|
| SD3.5 512 최종 | 384 | 약 0.4 |
| SD3.5 1024 최종 | 384 | 약 1.7 |
| FLUX 512 최종 | 384 | 약 0.7 |
| FLUX 1024 최종 | 384 | 약 2.7 |
| 평가 (특징, Vendi, 판정기) | | 약 1 |
| **합계** | | **약 6.5** |

- E01에서 잰 시간을 썼다: SD3.5 1024 장당 약 16초, FLUX 1024 장당 약 25초.
- GPU 4개를 다른 세션 작업(E03 klein, E02)이 함께 쓰고 있어, 빈 메모리에 따라 더 걸릴 수 있다. FLUX 1024는 약 34 GB가 비어야 시작한다.
- 대기열은 E01의 `job_queue.py`를 쓴다. 메모리 충돌로 한 작업이 재시도 한도를 다 쓰면, 같은 명령을 새 이름으로 다시 넣는다.
